# 개발 규칙

이 문서는 `AGENTS.md`의 상세 절차를 정의한다. 저장소 루트의 `AGENTS.md`와 함께 관리한다.
목표는 기능의 정확성과 하위호환을 유지하면서 개발자의 이해 부채를 줄이는 것이다.
모든 작업은 공통 규칙을 적용하고, 해당 작업 유형의 절을 추가로 적용한다.

## 공통 규칙

### 1. 설계·구현 판단 전: 기존 구조 확인

판단에 필요한 관련 코드를 반드시 직접 확인한다.

- 기존 동작, 호출 관계, API 계약 및 데이터 구조를 확인한다.
- 모듈 책임, 의존 관계 및 데이터 경계는 `docs/ARCHITECTURE.md`의 관련 내용을 확인한다.
- 코드를 확인하지 않고 추측만으로 설계하거나 구현하지 않는다.
- 함수·라이브러리는 실제 구현 코드 또는 사용 중인 버전의 공식 문서로 입력·반환값, 예외 및 부수 효과를 확인한다.
- 확인만으로 동작이 명확하지 않으면 테스트나 재현 코드로 검증한 뒤 사용한다.
- 확인 범위는 해당 판단에 필요한 부분으로 제한한다. 이해를 돕지 않는 전수 조사나 반복 확인은 피한다.

### 2. 구현 중: 단순하고 추적 가능한 코드

요구사항대로 정상 작동한다는 전제하에 최대한 단순하게 구현한다.

- 기존 구조와 관례를 우선 활용한다. 기존 구조 자체가 문제라면 근거와 변경 범위를 설명한다.
- 미래 확장 가능성만을 이유로 추상화, 계층, 의존성, 공통 프레임워크나 요구되지 않은 기능을 추가하지 않는다.
- 추상화를 추가한다면 현재 해결하는 문제와 직접 구현보다 나은 이유를 설명한다.
- 호출 전달만 하는 함수와 과도한 파일 분리를 피한다. 단, 모듈 경계나 계약 유지에 필요한 위임은 그 목적에 따라 판단한다.
- 도메인 용어로 이름을 짓고, 중요한 상태 변경과 부수 효과를 드러낸다.
- 코드 줄 수를 줄이려고 지나치게 압축하거나, 흐름을 숨기는 고차 함수·체인을 만들지 않는다.
- 관련 없는 리팩터링을 섞지 않는다. 필요하면 별도 작업으로 제안한다.
- 큰 변경은 개발자가 각각 이해하고 검증할 수 있는 단위로 나눈다. 미완성인 단계는 완료된 기능으로 보고하지 않는다.
- 개발자가 단계별 검토를 요청했거나 설계에서 검토 지점을 합의했다면 해당 지점에서 다음 구현 전 검토를 받는다. 모든 작은 변경마다 승인 절차를 만들지는 않는다.

### 3. 필요한 주석

코드만으로 알기 어려운 의도나 제약을 필요한 만큼 간결하게 설명한다.

- 주석은 해당 함수·클래스의 동작만으로 이해되도록 작성한다.
- 설계 문서의 절 번호, Phase, ADR 번호나 부록을 읽어야만 의미를 알 수 있는 표현을 쓰지 않는다. 필요한 규칙과 제약을 주석 안에 직접 짧게 적는다.
- 함수 내부의 핵심 업무 처리 단계 바로 위에는 도메인 용어로 무엇을 하는지 한 문장을 적는다. 단계 주석을 읽으면 주요 흐름을 따라갈 수 있게 한다.
- 중요한 분기·검증 단계는 조건과 그 결과(중단, 예외, 재시도, 건너뜀 등)를 함께 적는다. 필요하면 이유를 덧붙인다.
- 문장은 `~한다.` 형태의 평서문으로 끝낸다.
- 단순 변수 선언, 자명한 위임·조회처럼 코드만으로 명확한 단계에는 억지로 주석을 붙이지 않는다.
- 주석은 코드와 함께 갱신한다. 흐름 자체가 복잡하면 주석을 늘리기 전에 코드를 단순화할 수 있는지 검토한다.

```kotlin
// 피한다: §3.2.3 · SELF + OWNER/ADMIN 관점 발행
// 권장: 대상자 본인 알림과 OWNER·ADMIN 관점 알림을 같은 트랜잭션에 발행한다. 행위자는 수신자에서 제외한다.

// 피한다: findById로 outbox 조회, 없으면 예외
// 권장: 워커가 선점한 아웃박스를 조회한다. 선점 후 삭제돼 행이 없으면 영구 실패로 처리한다.
// 피한다: status 체크
// 권장: 처리 대기(PENDING) 상태인지 확인한다. 이미 완료·실패 처리된 아웃박스면 처리를 중단한다.
```

위 예시의 영구 실패·중단 정책은 해당 도메인에서 그 동작이 맞는 경우에만 사용한다.

### 4. 구현 후: 검증과 이해 확인

- 변경에 필요한 테스트·빌드 등 검증을 수행하고 실제 결과를 보고한다.
- 불필요한 분기, 중복, 우회 호출, 현재 필요 없는 추상화를 제거할 수 있는지 검토한다.
- 주요 변경은 아래 내용을 실제 코드의 함수·파일과 연결해 간결하게 설명한다. 단순 수정은 변경점과 검증 결과에 맞춰 설명을 줄인다.

| 항목 | 설명할 내용 |
| --- | --- |
| 실행 흐름 | 진입점 → 주요 함수 → 상태·DB 변경 → 응답 또는 후속 처리 |
| 실패 처리 | 중요한 실패 지점과 남는 상태, 재시도·중복 요청 처리 |
| 설계 선택 | 복잡한 구조가 필요했던 이유와 감수하는 제약 |
| 변경 위치 | 예상되는 요구사항 변경 시 수정할 함수·파일과 영향 범위 |
| 검증 결과 | 확인한 동작, 실행한 검증, 미검증·미완성 범위 |

DB·외부 연동·비동기 작업이 있으면 해당되는 트랜잭션 경계, 외부 호출 실패, 재시도 및 중복 처리도 설명한다. 해당되지 않는 항목을 억지로 추가하지 않는다.

개발자가 스스로 확인할 핵심 질문을 작업에 맞춰 최대 세 개 제시한다. 일반적인 기준은 다음과 같다.

1. 요청이 어떤 함수들을 거쳐 상태를 변경하는가?
2. 중간 실패 후 어떤 상태가 남으며, 재시도는 안전한가?
3. 요구사항 하나가 달라지면 어디를 고쳐야 하는가?

에이전트는 구현·검증 상태를 보고하되 개발자의 이해 여부를 대신 판단하지 않는다. 개발자가 이해가 어렵다고 말하면 실제 코드와 연결해 설명하고, 구조가 원인이라면 단순화 방안을 제안한다.
긴 설명이나 문서 추가만으로 불필요한 복잡성을 정당화하지 않는다.

## 설계가 필요한 작업

### 5. 구현 착수 전: 설계 합의 및 ADR 작성

신규 기능이나 리팩터링처럼 설계가 필요한 개발은 개발자와 문답식으로 논의한 뒤 구현한다.

- 대화를 통해 정확한 기획 내용을 파악한다.
- 요구사항, 구현 방향, 영향 범위를 합의하기 전에는 구현을 시작하지 않는다.
- 요청부터 응답까지의 실행 흐름과 주요 실패 지점, 해당되는 트랜잭션·외부 연동 경계를 설명한다.
- 이미 합의한 내용은 반복 승인받지 않는다. 합의 범위를 벗어나는 중요한 변경은 다시 논의한다.
- 설계가 완료되면 ADR을 작성한다. 개발자가 “설계안을 작성해줘.”라고 요청한 경우에도 ADR 파일을 작성한다.
- 설계 판단이 필요 없는 오탈자·설명 수정이나 단순 수정에 새 ADR을 강제하지 않는다. 버그 수정이라도 새로운 설계가 필요하면 이 절을 적용한다.

설계 문서 경로:

`docs/adr/[관련 모듈]/[XXXX]-[title]-adr.md`

`XXXX`는 해당 디렉토리의 기존 번호를 확인해 정하는 순차 번호다. 저장소에 별도 번호 정책이 있다면 그 정책을 따른다.

| 항목 | 작성 내용 |
| --- | --- |
| 개요 | 설계의 배경과 해결하려는 문제 |
| 목적 | 달성하려는 목표 |
| 설계 내용 | 구현 구조, 실행 흐름, 상태 변경과 주요 실패 처리 |
| 검토한 대안 | 실제로 고려한 대안별 장단점 |
| 트레이드오프 | 선택 근거와 감수하는 제약, 복잡성을 추가한 이유 |
| 구현 순서(Phase) | 단계별 구현·검증 범위와 필요한 개발자 검토 지점 |

항목을 채우기 위해 불필요한 대안을 만들거나 문서를 장황하게 늘리지 않는다.

### 6. 각 구현 단계 진행 및 완료 시: 구현 기록

설계를 토대로 구현할 때는 각 Phase의 진행 내용을 기존 구현 문서에 누적 기록한다.

구현 문서 경로:

`docs/impl/[관련 모듈]/[XXXX]-[관련 title]-impl.md`

테스트 관련 설계의 구현 기록은 다음 경로에 둔다. 이는 구현 기록의 경로 예외이며 설계 합의나 ADR 작성의 면제를 뜻하지 않는다.

`docs/test/[관련 모듈]/impl/[XXXX]-[관련 title]-impl.md`

필수 내용:

- 관련 설계 문서 링크
- Phase별 구현 내용과 핵심 실행 흐름의 변경
- 관련 커밋 해시와 요약. 미커밋이면 해당 상태를 표시한다.
- 검증 결과와 아직 완료되지 않은 범위
- 설계 대비 변경 사항과 그 이유
- 다음 변경 시 알아야 할 수정 위치와 후속 작업

실행 흐름이 ADR과 같다면 링크하고 달라진 부분만 기록한다. 코드를 그대로 옮겨 적거나 매 단계 별도 설명 문서를 추가하지 않는다.
구조가 변경되면 `docs/ARCHITECTURE.md`의 관련 내용도 갱신한다.

## API·DB 변경

### 7. API·DB 하위호환

API와 DB 변경은 반드시 하위호환을 유지한다.

- 기존 클라이언트의 요청·응답 계약과 기존 애플리케이션의 DB 사용이 깨지지 않게 한다.
- 기존 API 필드·DB 컬럼을 삭제하거나 이름을 변경하지 않는다. 새 필드·컬럼을 추가한 뒤 점진적으로 반영한다.
- 롤링 배포에서 구버전·신버전 애플리케이션이 함께 실행되는 상황과 기존 데이터도 확인한다.

### 8. 엔티티·DTO의 Enum 사용

`notificationType`처럼 값의 종류가 정해져 있어 Enum이 적절한 필드는 String 대신 Enum을 사용한다.

- 개발자가 허용되는 값의 종류를 코드에서 명확히 파악할 수 있게 한다.
- DB 컬럼은 `VARCHAR` 등 문자열 타입으로 정의하고 Enum 값을 문자열로 저장한다.
- DB 네이티브 ENUM과 ordinal은 사용하지 않는다.
- Enum 값을 추가·변경할 때 기존 API 소비자와 구버전 애플리케이션의 역직렬화·DB 읽기에 미치는 영향도 확인한다.

### 9. Flyway 마이그레이션

DB 구조 변경 및 기존 데이터 보정은 반드시 새 Flyway 마이그레이션 파일을 통해 진행한다.
이미 적용된 파일의 내용이나 이름을 변경하지 않는다.

파일명은 기존 정책대로 분 단위 타임스탬프를 사용한다.

```text
V<yyyyMMddHHmm>__<설명>.sql
예: V202609301530__email_verifications_login_otp_purpose.sql
```

- 기존 순차 번호(`V001`~`V080`) 파일은 그대로 둔다. 이 형식의 새 타임스탬프 버전은 기존 번호보다 뒤에 정렬된다.
- 타임스탬프는 순차 번호의 수동 조율을 줄이지만 같은 분에 생성하면 충돌할 수 있다. 파일 추가 전과 머지 전 버전 중복을 확인한다.
- 중복 발견 시 아직 어느 환경에도 적용되지 않은 새 파일의 버전만 조정한다. 적용 이력이 있으면 이름을 바꾸지 않고 원인과 해결 절차를 먼저 확인한다.
- 프로젝트에서 실제 사용하는 시간대·버전 생성 관례를 확인해 따른다. 이번 개정만으로 파일명 체계를 바꾸지 않는다.
- `out-of-order`의 활성화 여부는 실제 실행 환경의 설정으로 확인한다. 문서에 적혀 있다고 활성화된 것으로 가정하지 않는다.
- `out-of-order=true`는 이미 적용된 최신 버전보다 낮은 버전의 미적용 마이그레이션을 실행할 수 있게 하는 설정이다. 버전 중복, SQL 실패, 마이그레이션 사이의 의존 관계나 순서 변경에 따른 결과 차이를 해결하지는 않는다.
- 마이그레이션이 다른 변경에 의존하면 적용 순서와 빈 DB에서의 전체 실행, 기존 DB에서의 업그레이드 결과를 필요한 범위에서 검증한다.

### 10. API 개발 완료 시: Swagger 문서화

신규·변경 API는 반드시 Swagger(OpenAPI) 문서를 작성·갱신한다.

다음 내용을 실제 구현과 일치하도록 문서화한다.

- API 기능
- 요청 파라미터와 본문
- 응답
- 오류 응답

## 테스트 작업

### 11. 테스트 진행 시: 테스트 결과 기록

개발자가 테스트 진행을 요청하면 테스트를 실행한 뒤 결과를 테스트 문서로 작성한다.
구현에 필요한 검증 자체는 별도 요청이 없어도 수행한다. 이 절의 상세 테스트 보고서는 개발자가 테스트 진행을 요청한 경우에 적용하며, 나머지 검증 결과는 구현 기록이나 완료 보고에 남긴다.

테스트 문서 경로:

`docs/test/[관련 모듈]/[XXXX]-[title]-test.md`

| 항목 | 작성 내용 |
| --- | --- |
| 목적·범위 | 검증하려는 동작과 테스트 경계, 기존 테스트와의 관계 |
| 테스트 환경 | DB·JDK·Docker 등 실행 환경과 버전 |
| 테스트 계정 | 실제 계정 사용 시 이메일·사용자 id·서비스(ODiiN/MSP)·조직·역할·인증 방식과 수행한 케이스 |
| 테스트 케이스 | 시나리오별 준비 데이터, 기대 결과, 실제 결과 |
| 실행 결과 | 통과·실패·skip 건수, 재현 가능한 실행 명령 |
| 변경 사항 | 추가·수정한 테스트 파일과 빌드 설정, 커밋 해시 또는 미커밋 상태 |
| 발견한 이슈 | 실행 중 발견한 결함·환경 문제와 조치 |
| 한계·후속 작업 | 검증하지 못한 범위와 개발자가 알아야 할 후속 작업 |

- 실패한 테스트도 숨기지 않고 관련 실제 출력과 원인을 기록한다. 원인이 불명확하면 가설과 확인된 사실을 구분한다.
- 테스트 케이스마다 사용 계정을 알 수 있게 한다. 행위자·수신자가 다르면 역할을 구분한다.
- 단위 테스트처럼 실제 계정이 필요 없으면 계정 항목을 해당 없음으로 표시한다.
- 토큰·비밀번호·인증번호 값은 기록하지 않으며 테스트 출력에서도 제거한다.

## 버그·프론트엔드 요청 분석

### 12. 원인 분석 설명

버그나 프론트엔드 요청의 분석 결과는 아래 세 항목으로 나눠 핵심만 간략하게 설명한다.
신입~주니어 개발자도 바로 이해할 수 있는 수준으로 쓴다.

| 항목 | 작성 내용 |
| --- | --- |
| 원인 | 문제를 일으킨 실제 코드 위치(`파일:라인`)와 무엇이 잘못됐는지 한두 문장 |
| 원인 발생 흐름 | API → 호출 함수 → 생성·전달 객체 → 문제 지점 순서의 번호 목록. 단계마다 한 문장 |
| 해결 방안 | 수정할 위치와 방법을 번호 목록으로 |

- 같은 원인에서 생기는 다른 증상은 흐름 아래에 한두 줄로 덧붙인다.
- 검토한 대안 비교, SDK·명세 확인 과정 같은 부가 설명은 개발자가 요청할 때만 쓴다.
- 선택이 필요하면 해결 방안 끝에 판단할 선택지를 한 줄로 묻는다.
- 원인이 확정되지 않았다면 단정하지 않고 확인된 사실과 추가 확인 사항을 표시한다.
- 수정 후에는 검증 결과와 남은 한계를 덧붙인다. 위 흐름으로 핵심 동작과 실패 처리를 이미 설명했다면 공통 규칙의 완료 설명을 중복 작성하지 않는다.
