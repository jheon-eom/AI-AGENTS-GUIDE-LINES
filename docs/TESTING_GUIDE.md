# 테스트 코드 작성 가이드

> 적용 대상: 모든 프로그래밍 언어, 프레임워크, 애플리케이션 유형 및 AI 코딩 에이전트.
>
> 목적: 적은 수의 가치 있는 테스트로 비즈니스 계약을 보호하고, 테스트 자체를 다음 개발자와 AI 세션이 읽을 수 있는 실행 가능한 명세로 유지한다.

## 1. 최우선 원칙

- **테스트의 목적은 통과, 개수, 커버리지 달성이 아니라 실제 결함 탐지와 비즈니스 계약 보호다.**
- 현재 구현의 동작을 무조건 올바른 요구사항으로 취급하지 마라.
- 비즈니스 행위와 외부에서 관찰 가능한 결과를 검증하고, 구현 세부사항에 과도하게 결합하지 마라.
- 기존 테스트를 통과시키기 위해 기대값이나 검증 강도를 임의로 변경하지 마라.
- 충분히 가치 있는 테스트만 추가하라. 테스트 추가 자체를 완료 조건으로 삼지 마라.
- 사용 중인 언어, 프레임워크, 테스트 도구 및 저장소의 기존 규칙을 우선 확인하라. 특정 기술이나 테스트 형태를 일률적으로 강제하지 마라.

## 2. 테스트 작성 전 확인 순서

1. 요구사항, 사용자 시나리오, 도메인 규칙, API/이벤트/데이터 계약을 확인한다.
2. 관련 기존 테스트를 읽고 이미 보호하는 행동과 누락된 위험을 파악한다.
3. 대상 구현과 실제 호출 경로, 상태 변경, 외부 의존성을 확인한다.
4. 기대 동작의 근거를 **확정된 요구사항 / 기존 계약 / 추정**으로 구분한다.
5. 근거가 부족하거나 서로 충돌하면 추측으로 기대값을 만들지 말고 불확실성을 명시한다. 안전하게 진행 가능한 범위만 진행한다.
6. 변경이 어떤 기존 계약을 깨뜨릴 수 있는지 먼저 확인한다.

## 3. 필요한 테스트만 선정

테스트 후보마다 아래 질문으로 검토한다.

- 고객, 데이터, 금전, 보안, 서비스 신뢰성에 실질적인 영향을 주는 규칙인가?
- 현실적인 잘못된 변경이나 장애를 탐지할 수 있는가? **이 테스트를 실패시킬 구체적인 버그는 무엇인가?**
- 동일한 행위를 기존 테스트가 충분히 검증하고 있지는 않은가?
- 더 간단하거나 빠른 수준에서 같은 위험을 안정적으로 검증할 수 있는가?
- 실패했을 때 문제를 이해하고 조치할 수 있는가?

정상 흐름을 기본으로 하되, 위험에 해당할 때에만 실패·경계 조건을 추가한다. 특히 권한, 입력 검증, 중복·멱등성, 트랜잭션·일관성, 동시성, 재시도, 장애 복구, 시간·순서 의존성을 검토한다.

다음 테스트는 원칙적으로 피한다.

- 의미 없는 getter/setter, 프레임워크 자체 기능 확인
- 기존 테스트와 동일한 계약을 별다른 탐지 가치 없이 반복
- Mock 호출만 확인하고 실제 의미 있는 결과를 검증하지 않는 테스트
- 구현 줄 수나 분기를 그대로 복제한 테스트
- 위험이 없는 단순 변경에 형식적으로 추가한 테스트

필요한 시나리오가 없으면 **새 테스트를 작성하지 않은 이유**를 보고한다.

## 4. 적절한 테스트 수준 선택

- **단위 테스트:** 순수 계산·정책·상태 전이 등 의존성을 최소화해 검증할 수 있는 규칙.
- **통합 테스트:** DB 제약·쿼리·트랜잭션, 메시징, 파일 시스템, 구성 요소 간 계약 등 실제 연동이 검증 대상인 경우.
- **계약 테스트:** API·이벤트·스키마 등 제공자와 소비자 사이의 약속을 보호해야 하는 경우.
- **E2E 테스트:** 핵심 사용자 흐름을 실제 경계 전체에서 확인해야 하며 하위 테스트만으로 충분하지 않은 경우.

가장 가벼우면서도 해당 결함을 실제로 탐지할 수 있는 수준을 선택한다. 빠르다는 이유만으로 실제 연동이 핵심인 검증을 가짜 객체로 대체하지 않는다. 반대로 단순 정책 검증을 위해 전체 애플리케이션을 기동하지 않는다.

## 5. Mock / Stub / Fake 사용 기준

- 통제가 필요한 **외부 경계**(서드파티 API, 과금 서비스, 네트워크 장애, 시간, 난수 등)에 주로 사용한다.
- 테스트 대상 비즈니스 로직 자체는 Mock 처리하지 않는다.
- Mock이 실제 동작의 결함을 숨길 수 있는지 먼저 검토한다.
- DB의 실제 쿼리·제약·락·트랜잭션을 검증할 때는 해당 동작을 구현하는 저장소/DB를 사용한다.
- 외부 시스템을 대체할 때는 성공뿐 아니라 해당 기능에 중요한 실패, 지연, 타임아웃, 중복 응답, 응답 유실 등을 필요한 만큼 재현한다.
- 호출 횟수·호출 순서는 그것이 업무 계약이거나 외부 부작용을 막는 중요한 조건일 때에만 검증한다.
- 테스트를 통과시키기 위해 Mock 응답을 실제 계약과 다르게 조작하지 않는다.

## 6. 테스트를 실행 가능한 비즈니스 명세로 작성

- 테스트 이름에 **조건 + 행동 + 기대 결과**가 드러나게 한다.
- 준비(Given) / 실행(When) / 검증(Then)을 읽기 쉽게 구분한다. 언어나 팀 관례에 맞는 표현을 사용한다.
- 한 테스트는 하나의 주요 비즈니스 규칙 또는 사용자 행동을 보호한다. 그 행동으로 발생하는 여러 관련 결과는 함께 검증해도 된다.
- 반환값뿐 아니라 중요한 영속 상태, 이벤트, 외부 부작용, 실패 후 변경되지 않아야 할 상태를 검증한다.
- 단순 HTTP 상태 코드, 예외 발생 여부, Mock 호출 여부만으로 계약 검증이 충분한지 점검한다.
- 테스트 데이터에는 의미 있는 값만 명시하고 숨겨진 전역 fixture와 과도한 추상화를 피한다.
- 모호한 요구사항은 테스트 이름이나 주석으로 확정된 사실처럼 서술하지 않는다.
- 요구사항 식별자나 설계 문서 링크가 있다면 핵심 계약 테스트와 연결한다.

**좋은 이름 예:** `잔액이 부족하면 결제를 거절하고 잔액을 변경하지 않는다`

**나쁜 이름 예:** `testPayment2`, `serviceCallsSaveOnce` (호출 횟수 자체가 계약이 아닌 경우)

## 7. 기존 테스트와 요구사항 변경 보호

기존 테스트가 실패하면 순서대로 확인한다.

1. 구현 결함인지, 테스트 환경·데이터 문제인지, 합의된 요구사항 변경인지 구분한다.
2. 기존 비즈니스 계약과 변경된 명세를 대조한다.
3. 요구사항 변경이 확인된 경우에만 기대값을 수정하고 근거를 남긴다.
4. 구현 결함이면 테스트를 약화하지 말고 구현을 수정한다.

**금지:** 실패를 숨기기 위한 assertion 삭제·완화, 테스트 건너뛰기, 예외 무시, Mock 반환값 조작, 타임아웃 무작정 증가, 취약한 재시도로 통과시키기.

테스트 자체가 잘못되었다는 근거가 있다면 수정할 수 있지만 무엇이 잘못되었는지와 유지되는 계약을 설명한다.

## 8. 독립성·결정성·실행 비용

- 테스트 간 데이터, 전역 상태, 캐시, 파일, 포트, 계정의 간섭을 막는다. 테스트 실행 순서에 의존하지 않는다.
- 시간·난수 등 비결정성을 통제하고 비동기 동작은 완료 조건과 제한 시간으로 기다린다. 고정 sleep에 의존하지 않는다.
- 필요한 최소한의 fixture를 사용하고, 무거운 환경 초기화는 안전한 범위에서 재사용한다.
- 언어/프레임워크가 제공하는 격리·정리 도구와 프로젝트 관례를 따른다.
- 느린 테스트는 실제 측정을 근거로 환경 기동, 데이터 준비, 실행, 대기, 정리 중 무엇이 병목인지 구분한다.
- CI의 필수 회귀 검증을 유지하면서 중복 실행과 과도한 E2E를 줄인다. 속도를 위해 중요한 검증을 제거하지 않는다.
- 병렬 실행 전 자원 충돌과 격리 가능성을 확인한다.

## 9. 에이전트 작업 절차

1. **분석:** 요구사항·기존 테스트·구현·테스트 환경을 확인한다.
2. **선정:** 보호할 계약, 탐지할 결함, 기존 테스트와의 중복 여부를 검토한다.
3. **설계:** 가장 적절한 테스트 수준과 실제/대체 의존성을 결정한다.
4. **작성:** 명확한 이름과 관찰 가능한 검증 결과를 갖춘 최소 테스트를 만든다.
5. **검증:** 변경된 테스트부터 실행하고 관련 회귀 테스트 및 프로젝트 필수 검증으로 확장한다.
6. **자체 평가:** 아래 체크리스트를 검토하고 불필요하거나 취약한 테스트를 개선한다.
7. **보고:** 보호한 규칙, 제외한 후보, 실행 결과, 미검증 위험을 간결하게 기록한다.

작업 규모가 작다면 내부적으로 간단히 수행한다. 모든 단계에 형식적인 문서나 장황한 보고를 만들 필요는 없다.

### 최종 자체 평가 체크리스트

- [ ] 테스트가 보호하는 비즈니스 계약을 한 문장으로 설명할 수 있다.
- [ ] 이 테스트에 걸리는 현실적인 결함을 설명할 수 있다.
- [ ] 기존 테스트와 목적이 불필요하게 중복되지 않는다.
- [ ] 현재 구현에 기대 결과를 무비판적으로 맞추지 않았다.
- [ ] 핵심 로직을 Mock 처리하지 않았고, 대체한 의존성의 근거가 있다.
- [ ] 실제 결과와 중요한 상태 변화(또는 비변경)를 검증한다.
- [ ] 테스트 이름과 데이터만으로 조건과 요구사항을 이해할 수 있다.
- [ ] 리팩터링만으로 불필요하게 깨질 구현 세부사항 검증을 피했다.
- [ ] 독립적이고 결정적이며 실행 비용이 검증 가치에 맞는다.
- [ ] 필요한 범위를 실제 실행했고, 미실행 항목은 명시했다.

## 10. 결과 보고 형식

작업 완료 시 필요에 따라 다음을 간략히 보고한다.

- **보호한 계약:** 어떤 사용자 행동·비즈니스 규칙을 검증했는가
- **추가/수정 테스트:** 무엇을 왜 작성하거나 변경했는가
- **제외한 후보:** 중복이거나 가치가 낮아 생략한 테스트와 이유
- **대체 의존성:** 사용한 Mock/Fake와 선택 이유
- **실행 결과:** 실제 실행 명령, 성공·실패, 확인하지 못한 범위
- **남은 위험:** 테스트로 확인하지 못한 중요한 계약이나 환경

테스트를 실행하지 않았으면 통과했다고 주장하지 않는다. 실측값과 추정값을 구분한다.
