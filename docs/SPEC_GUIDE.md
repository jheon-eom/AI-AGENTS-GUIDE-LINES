# SPEC_GUIDE.md — 행동 기반 스펙 작성 가이드

## 1. 목적

본 문서는 AI 에이전트가 소프트웨어의 비즈니스 요구사항을 명확하게 이해하고, 구현하고, 검증할 수 있도록 스펙 작성 규칙을 정의한다.

모든 기능의 요구사항은 **Context → Trigger → Reaction** 구조로 표현한다.

- **Context (전제)**: 행위가 발생하기 전 시스템의 상태와 조건
- **Trigger (행위)**: 사용자, 시스템 또는 외부 서비스가 수행하는 사건
- **Reaction (결과)**: 행위 이후 시스템이 반드시 보장해야 하는 결과

스펙은 구현 방법보다 **외부에서 관찰할 수 있는 비즈니스 동작**을 우선적으로 기술한다.

## 2. 작성 원칙

### 2.1 하나의 시나리오는 하나의 행동을 정의한다

하나의 시나리오에는 명확한 전제, 하나의 주요 행위, 그에 따른 기대 결과를 작성한다.

하나의 행위에서 발생하는 여러 결과는 동일한 Reaction에 포함할 수 있다.

서로 다른 전제나 행위를 가진 경우 별도의 시나리오로 분리한다.

### 2.2 모호한 표현을 금지한다

다음과 같은 표현을 피한다.

- 적절히 처리한다.
- 빠르게 응답한다.
- 필요하면 차단한다.
- 정상적으로 저장한다.
- 오류를 처리한다.

가능한 한 구체적인 값, 상태, 조건, 결과를 명시한다.

### 2.3 구현 방법을 강제하지 않는다

스펙은 비즈니스 행동을 정의하는 문서다.

특별한 기술적 제약이 없다면 데이터베이스, 캐시, 클래스, 함수, 라이브러리 등의 구현 세부사항을 요구사항에 포함하지 않는다.

예를 들어 다음과 같이 작성한다.

- 권장: 계정은 잠금 해제 시각 이전까지 로그인할 수 없다.
- 비권장: Redis에 TTL 1800초인 키를 저장한다.

### 2.4 모든 시나리오는 검증 가능해야 한다

각 Reaction은 테스트 또는 명확한 검증 절차로 확인할 수 있어야 한다.

검증할 수 없는 추상적인 목표는 구체적인 인수 조건으로 변환한다.

### 2.5 결정되지 않은 정책을 추측하지 않는다

AI 에이전트는 스펙에 명시되지 않은 중요한 비즈니스 정책을 임의로 확정하지 않는다.

정책이 모호하거나 기존 요구사항과 충돌하면 이를 미결정 사항으로 기록하고 필요한 경우 사용자에게 확인한다.

## 3. 스펙 작성 템플릿

### SPEC-001: [기능 또는 행동 이름]

**Context**
- [행위가 발생하기 전 시스템 상태]
- [행위가 유효한 조건]

**Trigger**
- [발생하는 사용자 또는 시스템 행위]

**Reaction**
- [변경되어야 하는 시스템 상태]
- [사용자 또는 외부 시스템에 반환되는 결과]
- [반드시 유지되어야 하는 비즈니스 규칙]

**관련 정책**
- [다른 시나리오에서 참조할 공통 규칙이 있는 경우]

## 4. 작성 예시: 로그인 실패 시 계정 잠금

### 공통 정책

- 동일 계정에서 비밀번호 인증을 연속 5회 실패하면 계정을 잠근다.
- 잠금 기간은 잠금이 발생한 시점부터 30분이다.
- 잠금 상태에서는 비밀번호가 올바르더라도 로그인을 허용하지 않는다.
- 잠기지 않은 계정에서 로그인에 성공하면 연속 실패 횟수를 초기화한다.

### SPEC-AUTH-001: 다섯 번째 로그인 실패 시 계정 잠금

**Context**
- 계정이 존재한다.
- 해당 계정에서 비밀번호 인증을 연속 4회 실패했다.
- 계정은 현재 잠겨 있지 않다.

**Trigger**
- 사용자가 동일 계정으로 잘못된 비밀번호를 입력해 로그인을 시도한다.

**Reaction**
- 연속 로그인 실패 횟수가 5회가 된다.
- 계정이 잠금 상태로 변경된다.
- 잠금 해제 시각은 현재 시각으로부터 30분 후로 설정된다.
- 로그인은 거부된다.
- 사용자에게 계정 잠금 안내 메시지를 반환한다.

### SPEC-AUTH-002: 계정 잠금 중 로그인 시도

**Context**
- 계정이 잠금 상태다.
- 현재 시각은 잠금 해제 시각보다 이전이다.

**Trigger**
- 사용자가 올바른 비밀번호로 로그인을 시도한다.

**Reaction**
- 로그인이 거부된다.
- 계정의 잠금 상태가 유지된다.
- 사용자에게 계정 잠금 안내 메시지를 반환한다.

### SPEC-AUTH-003: 로그인 성공 시 실패 횟수 초기화

**Context**
- 계정은 잠겨 있지 않다.
- 연속 로그인 실패 횟수가 1회 이상 4회 이하다.

**Trigger**
- 사용자가 올바른 비밀번호로 로그인을 시도한다.

**Reaction**
- 로그인이 성공한다.
- 연속 로그인 실패 횟수가 0회로 초기화된다.

### SPEC-AUTH-004: 잠금 기간 만료 후 로그인

**Context**
- 계정은 로그인 실패로 잠긴 상태였다.
- 현재 시각이 잠금 해제 시각과 같거나 이후다.

**Trigger**
- 사용자가 올바른 비밀번호로 로그인을 시도한다.

**Reaction**
- 이전 잠금으로 인해 로그인이 거부되지 않는다.
- 다른 로그인 제한이 없다면 로그인이 성공한다.
- 잠금 상태와 연속 실패 횟수가 초기화된다.

## 5. AI 에이전트 실행 규칙

AI 에이전트는 기능을 구현하거나 수정할 때 다음 절차를 따른다.

1. 관련 스펙과 기존 코드를 확인한다.
2. Context가 어떤 시스템 상태를 의미하는지 파악한다.
3. Trigger가 발생하는 실행 경로를 찾는다.
4. Reaction의 모든 조건이 만족되도록 구현한다.
5. 각 시나리오를 검증하는 테스트를 작성하거나 기존 테스트와 연결한다.
6. 정상 상황뿐 아니라 경계 조건과 예외 상황을 확인한다.
7. 구현 결과와 스펙 사이에 불일치가 없는지 검증한다.

테스트가 통과했다는 이유만으로 스펙을 만족했다고 판단하지 않는다. 테스트의 검증 내용이 Reaction을 실제로 보장하는지 확인한다.

## 6. 스펙과 테스트의 관계

- Context는 테스트의 초기 상태에 대응한다.
- Trigger는 테스트에서 실행하는 행위에 대응한다.
- Reaction은 테스트에서 검증해야 하는 결과에 대응한다.

각 시나리오에는 최소 하나 이상의 적절한 검증 방법이 있어야 한다.

테스트 종류나 개수는 기능의 위험도, 비즈니스 중요도, 기존 테스트 범위를 고려해 결정한다.

불필요한 중복 테스트나 구현 세부사항에만 의존하는 테스트는 피한다.

## 7. 변경 관리

기능을 변경할 때 AI 에이전트는 다음을 확인한다.

- 기존 스펙과 충돌하는가?
- 기존 시나리오의 Reaction이 달라지는가?
- 새로운 시나리오가 필요한가?
- 기존 테스트를 수정하거나 추가해야 하는가?

기존 스펙이 변경되는 경우, 변경된 비즈니스 정책이 코드와 테스트에 일관되게 반영되도록 한다.

**핵심 원칙: 스펙은 AI에게 코드를 작성하도록 지시하는 문서가 아니라, 시스템이 어떤 행동을 보장해야 하는지 정의하는 계약이다.**
