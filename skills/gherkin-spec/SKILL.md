Gherkin 명세 작성과 구현

저장소의 AGENTS.md 공통 지침을 함께 따른다. 아래 경로는 저장소 루트 기준이다.

요청에 따른 진행





작성·수정 요청: 관련 docs/spec/<주제>/의 결정 기록과 기능 명세를 읽고, 아래 작성 절차와 파일 구성 규칙을 따른다.



명세 기반 구현 요청: 관련 결정 기록과 기능 명세에서 합의된 시나리오와 미정 사항을 먼저 확인한 뒤, 아래 TDD 절차를 따른다. 구현에 필요한 정책이 미정이면 작성 절차로 돌아가 해당 정책을 한 가지씩 합의한다. 이미 합의된 정책을 다시 질문하지 않는다.



명세 작성 요청만으로 구현을 시작하지 않는다.

Gherkin 명세 작성

사용자와 대화하며 점진적으로 작성한다.





먼저 관련 명세에서 기존 결정과 미결 사항을 확인한다.



한 번에 한 가지 정책을 질문한다. 선택지가 있으면 차이와 추천안을 함께 제시한다.



사용자 답변을 Given · When · Then 시나리오에 반영해 보여준 뒤 다음 논점으로 넘어간다.



추천이나 추측을 확정 사항으로 쓰지 말고, 미합의 내용은 초안·미정으로 구분한다.



사용자가 내용을 추가하거나 기존 전제를 바꾸면 먼저 해당 시나리오를 갱신하고, 기존 결정의 변경 이력을 남긴다.



남은 논점은 우선순위로 관리하되 한꺼번에 답하도록 요구하지 않는다.

파일 구성과 번호





명세는 docs/spec/<주제>/에 둔다. 같은 사용자 흐름에 속한 기능은 같은 주제 폴더에 모은다. 예를 들어 회사 생성 이후의 구성원 계정 등록은 회사 폴더에 두며, 이름에 구성원이 들어간다는 이유만으로 인사에 분리하지 않는다.



결정 요약·변경 이력·미정 사항·후속 논의는 하나의 00. 문서로 묶는다. 파일명에도 결정 기록과 후속 논의라는 성격을 드러낸다. 예: 00.회사_계정_권한_결정_기록_후속_논의.md.



Gherkin 기능 명세는 기능이나 성격이 일관된 단위로 파일을 나눈다. 결정 기록 문서에 모든 시나리오를 넣지 않는다. 각 기능 파일은 해당 기능의 시나리오와 필요한 설명을 담는다.



기능 파일은 사용자가 겪는 순서대로 01.부터 두 자리 번호를 붙인다. 예: 01.회사_생성_메일_수신.md → 02.회사_생성자_권한.md → 03.구성원_등록.md → 04.관리자_권한_위임.md. 새 번호를 붙이기 전에 해당 폴더의 최신 파일을 확인하고, 기존 번호를 임의로 재사용하거나 재번호하지 않는다.



00. 문서에는 기능 명세 링크를 사용자 흐름 순서로 나열하고, 각 기능 명세에는 00. 문서로 돌아가는 링크를 둔다. 파일명이나 위치를 바꿀 때는 참조 링크도 함께 갱신하고 확인한다.

Gherkin 명세 기반 구현 — TDD 필수

합의된 Gherkin 명세를 구현할 때는 시나리오별로 다음 순서를 반복한다.





Red — 실패하는 테스트 작성: 시나리오의 비즈니스 요구사항을 검증하는 테스트를 먼저 작성하고 실행한다. 환경 오류가 아니라 해당 요구사항이 아직 구현되지 않아 실패하는지 확인한다.



Green — 최소 구현: 해당 테스트가 통과하는 데 필요한 최소한의 코드를 작성하고, 테스트가 통과하는지 확인한다.



Refactor — 리팩터링: 테스트가 통과하는 상태를 유지하면서 중복을 제거하고 코드 구조를 개선한다. 리팩터링 후 관련 테스트를 다시 실행하여 기존 동작이 유지되는지 확인한다.

구현 코드를 먼저 작성한 뒤 테스트를 덧붙이는 순서로 진행하지 않는다. 테스트는 구현 내부 구조가 아니라 Gherkin 명세의 비즈니스 동작과 결과를 검증한다.
