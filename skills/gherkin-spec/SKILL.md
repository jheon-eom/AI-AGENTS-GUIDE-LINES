# Gherkin 명세 작성과 구현

저장소의 `AGENTS.md` 공통 지침을 함께 따른다. 아래 경로는 저장소 루트 기준이다.

## 요청에 따른 진행

- **작성·수정 요청:** 관련 `docs/specs/<주제>/`의 결정 기록과 기능 명세를 읽고, 아래 작성 절차와 파일 구성 규칙을 따른다.
- **명세 기반 구현 요청:** 관련 결정 기록과 기능 명세에서 합의된 시나리오와 미정 사항을 먼저 확인하고, 해당 주제의 `docs/specs/<주제>/STATUS.yaml`에서 SPEC ID와 검증 근거를 대조한 뒤 TDD 절차를 따른다. 구현에 필요한 정책이 미정이면 작성 절차로 돌아가 해당 정책을 한 가지씩 합의한다. 이미 합의된 정책을 다시 질문하지 않는다.
- **구현 현황 점검 요청:** 실제 명세·상태 파일·관련 테스트와 코드를 대조한다. 상태 파일만 보고 구현이나 검증이 완료됐다고 단정하지 않는다.
- 명세 작성 요청만으로 구현을 시작하지 않는다.

## Gherkin 명세 작성

사용자와 대화하며 점진적으로 작성한다.

- 먼저 관련 명세에서 기존 결정과 미결 사항을 확인한다.
- 한 번에 한 가지 정책을 질문한다. 선택지가 있으면 차이와 추천안을 함께 제시한다.
- 사용자 답변을 `Given` · `When` · `Then` 시나리오에 반영해 보여준 뒤 다음 논점으로 넘어간다.
- 추천이나 추측을 확정 사항으로 쓰지 말고, 미합의 내용은 초안·미정으로 구분한다.
- 사용자가 내용을 추가하거나 기존 전제를 바꾸면 먼저 해당 시나리오를 갱신하고, 기존 결정의 변경 이력을 남긴다.
- 남은 논점은 우선순위로 관리하되 한꺼번에 답하도록 요구하지 않는다.

### 파일 구성과 번호

- 명세는 `docs/specs/<주제>/`에 둔다. 같은 사용자 흐름에 속한 기능은 같은 주제 폴더에 모은다. 예를 들어 구성원 등록·관리자 권한 위임·슈퍼계정의 인사 화면은 `인사` 폴더에 모은다(2026-11-05 사용자 결정). 폴더를 옮겨도 SPEC ID는 바꾸지 않는다.
- **결정 요약·변경 이력·미정 사항·후속 논의는 하나의 `00.` 문서로 묶는다.** 파일명에도 결정 기록과 후속 논의라는 성격을 드러낸다. 예: `00.회사_계정_권한_결정_기록_후속_논의.md`.
- **Gherkin 기능 명세는 기능이나 성격이 일관된 단위로 파일을 나눈다.** 결정 기록 문서에 모든 시나리오를 넣지 않는다. 각 기능 파일은 해당 기능의 시나리오와 필요한 설명을 담는다.
- 기능 파일은 사용자가 겪는 순서대로 `01.`부터 두 자리 번호를 붙인다. 예: `인사/01.구성원_등록.md` → `02.관리자_권한_위임.md` → `03.슈퍼계정_인사_전체_워크스페이스.md`. 새 번호를 붙이기 전에 해당 폴더의 최신 파일을 확인하고, 기존 번호를 임의로 재사용하거나 재번호하지 않는다.
- `00.` 문서에는 기능 명세 링크를 사용자 흐름 순서로 나열하고, 각 기능 명세에는 `00.` 문서로 돌아가는 링크를 둔다. 파일명이나 위치를 바꿀 때는 참조 링크도 함께 갱신하고 확인한다.

### 시나리오 식별자 (SPEC ID)

- **모든 Gherkin `Scenario`와 `Scenario Outline`에 고유하고 불변인 ID를 부여한다.** 명세가 Markdown 파일에 있어도 Gherkin 코드 블록 안의 시나리오 바로 위에 태그 `@SPEC-<DOMAIN>-NNN`을 붙인다. 예: `@SPEC-AUTH-001`. `DOMAIN`은 한 번 정한 짧은 영문 대문자 코드로 고정한다. `Scenario Outline`의 각 `Examples` 행은 별도 시나리오 ID로 분리하지 않는다.
- 새 ID를 만들기 전 **전체 `docs/specs/`와 상태 파일**에서 사용 중인 ID 및 마지막 번호를 확인한다. 다른 시나리오에 사용한 ID는 삭제·이동·폐기 이후에도 재사용하지 않는다. 파일 이동·제목 변경만으로 ID를 바꾸지 않는다.
- 요구사항이 실질적으로 교체되면 기존 ID의 이력을 보존하고 신규 ID 필요 여부를 판단한다. 시나리오 분리·병합 시 기존 ID를 무분별하게 재활용하지 않으며, 어느 ID를 유지·폐기했는지 결정 기록에 남긴다.
- ID는 비즈니스 행동을 식별한다. 단순한 `Given`/`Then` 단계, 기술 구현 단위, 테스트 메서드마다 새 ID를 만들지 않는다.

```gherkin
@SPEC-AUTH-001
Scenario: 비밀번호 인증 5회 실패 시 계정 잠금
  Given 같은 계정의 비밀번호 인증이 4회 연속 실패했다
  When 해당 계정의 비밀번호 인증이 다시 실패한다
  Then 해당 계정은 30분 동안 잠긴다
```

### 구현·검증 상태 추적

- **상태 원장은 주제별로 둔다** — `docs/specs/<주제>/STATUS.yaml`. 한 주제 폴더의 SPEC ID는 그 폴더의 원장에만 싣고, 다른 주제의 원장에 중복 기재하지 않는다. Gherkin 시나리오가 없는 주제에는 원장을 두지 않는다. `00.` 결정 기록 문서의 결정 표는 그대로 유지한다. Gherkin 본문·`00.` 표에 구현 상태나 업데이트 날짜를 중복 기재하지 않는다.
- 원장에는 SPEC ID를 키로 사용하고, **구현 상태**(`not_started` / `in_progress` / `implemented`)와 **검증 상태**(`not_run` / `passed` / `failed` / `stale`)를 분리한다. `implemented`는 관련 코드가 존재한다는 기록이지 현재 명세를 충족한다는 보증이 아니다.
- SPEC ID가 추가되면 원장에도 항목을 추가한다. 시나리오를 폐기하는 경우 원장 항목과 변경 이력을 즉시 삭제하지 말고 폐기 여부와 대체 ID를 추적할 수 있게 보존한다. 폐기 표시는 `retired: true`와 선택적인 `replaced_by`로 나타낸다.
- `tests`에는 대응하는 테스트의 **실제 파일 경로 또는 안정적인 테스트 식별자**를 기록한다. 실행하지 않았거나 실패한 테스트를 `passed`로 표기하지 않는다. `verified_spec_hash`는 검증을 통과한 **해당 시나리오 원문의 SHA-256**이다. 값을 추정하거나 예시 해시를 실제 검증값으로 복사하지 않는다.
- `updated_at`은 **상태 원장 항목이 실제 수정된 날짜(ISO 8601 `YYYY-MM-DD`)**로만 사용한다. 가능하면 Git/CI에서 자동으로 기록하고, 자동화 전에는 상태 변경 시에만 정확한 날짜를 기록한다. 날짜만 보고 구현·검증의 유효성을 판단하지 않는다.

```yaml
# docs/specs/<주제>/STATUS.yaml 예시 — 값은 실제 근거를 확인해 갱신
specs:
  SPEC-AUTH-001:
    implementation: not_started
    verification: not_run
    tests: []
    verified_spec_hash: null
    updated_at: null
```

#### 변경과 검증 규칙

1. 명세 수정 전후에 **시나리오별 변경 여부**를 확인한다. Given/When/Then/Examples의 의미가 바뀌었거나 기존 검증 당시의 시나리오 해시와 달라지면, 관련 항목을 `verification: stale`로 전환하고 재검토·재검증한다. 단순한 다른 시나리오 변경 때문에 무관한 SPEC ID를 `stale`로 만들지 않는다.
2. 의미 있는 변경이 없으면 기존 SPEC ID를 유지한다. 명세 변경만으로 `implementation: implemented`를 자동으로 `not_started`로 되돌리지 않는다. 단, **현재 명세 검증 완료로 취급하지 않는다.**
3. AI 에이전트가 코드를 작성했다는 이유만으로 구현·검증을 `implemented`·`passed`로 바꾸지 않는다. 실제 코드와 테스트의 연계, 요구사항 검토 및 테스트 실행 결과를 근거로 갱신한다. 검증을 못 했으면 `not_run` 또는 기존 실패·만료 상태를 유지하고 사유를 보고한다.
4. 명세의 신규·변경·폐기 또는 구현 상태 변경 작업이 끝나면 **SPEC ID 중복, 명세–원장 누락, 테스트 참조 유효성, 검증 해시 일치 여부**를 확인한다. CI가 아직 구현되지 않았다면 수동 검증 결과를 명시한다. CI가 존재한다고 추정하지 않는다.
5. 상태 원장은 에이전트 세션/Auto-Compact 이후 작업 재개용 인덱스다. **재개할 때는 원장뿐 아니라 관련 Gherkin·결정 기록·실제 코드와 테스트를 다시 읽는다.**

### Gherkin 명세 기반 구현 — TDD 필수

합의된 Gherkin 명세를 구현할 때는 시나리오별로 다음 순서를 반복한다. 작업 전에 해당 SPEC ID의 원장 상태와 현재 명세를 대조하고, 착수 시 구현 상태를 `in_progress`로 기록한다.

1. **Red — 실패하는 테스트 작성:** 시나리오의 비즈니스 요구사항을 검증하는 테스트를 먼저 작성하고 실행한다. 환경 오류가 아니라 해당 요구사항이 아직 구현되지 않아 실패하는지 확인한다.
2. **Green — 최소 구현:** 해당 테스트가 통과하는 데 필요한 최소한의 코드를 작성하고, 테스트가 통과하는지 확인한다.
3. **Refactor — 리팩터링:** 테스트가 통과하는 상태를 유지하면서 중복을 제거하고 코드 구조를 개선한다. 리팩터링 후 관련 테스트를 다시 실행하여 기존 동작이 유지되는지 확인한다.

구현 코드를 먼저 작성한 뒤 테스트를 덧붙이는 순서로 진행하지 않는다. 테스트는 구현 내부 구조가 아니라 Gherkin 명세의 비즈니스 동작과 결과를 검증한다.

Red–Green–Refactor 후에는 관련 테스트의 실제 통과와 시나리오 충족 여부를 확인하고, 근거가 있는 경우에만 `implementation: implemented`, `verification: passed`, 대응 테스트 경로, 현재 시나리오의 `verified_spec_hash`, `updated_at`을 함께 갱신한다. 검증이 실패했거나 미실행이면 완료로 기록하지 않고 현재 상태와 남은 작업을 보고한다.
